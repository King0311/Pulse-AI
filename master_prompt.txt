# Pulse AI — Project Master Specification

## Product

Build **Pulse AI**, a premium AI-powered fitness intelligence and adaptive training coach.

Tagline: "Train smarter. Recover better. Become stronger."

Pulse AI uses wearable health metrics, sleep, recovery, workout history, training goals and user preferences to generate actionable personalized training recommendations.

It is NOT just a wearable metrics dashboard or a generic AI chatbot.

The primary product value is:

**Collect health data → analyze trends → understand recovery → adapt training → explain recommendations.**

## Architecture

Keep frontend and backend separate.

Frontend:
apps/web

Backend:
apps/api

The frontend must never directly access the database.

The frontend communicates with FastAPI using REST.

The backend is responsible for:
- Authentication and authorization
- Data persistence
- Health metric calculations
- Readiness calculations
- Training logic
- AI context building
- AI recommendations
- Validation
- Data imports

Use a modular backend architecture with routers, services, repositories, models and schemas.

Do not place business logic inside API route handlers.

## Readiness Engine

Implement readiness calculations deterministically in Python.

Initial components:
- HRV status
- Resting heart rate status
- Sleep duration
- Sleep quality
- Recent training load

Initial prototype weights:
- HRV: 30%
- Resting heart rate: 20%
- Sleep duration: 25%
- Sleep quality: 15%
- Training load: 10%

These are prototype assumptions, not medically validated weights.

Normalize metrics relative to the user's own baseline.

Use rolling baselines where enough historical data exists.

When metrics are missing:
- Do not assign a score of zero.
- Exclude unavailable metrics.
- Re-normalize weights.
- Calculate data coverage.
- Reduce confidence when data is incomplete.

Do not pretend to have a personalized baseline when insufficient historical data exists.

---

## Adaptive Training Engine

Use deterministic rules to determine workout modifications.

Consider:
- Readiness
- Training load
- Recent workout history
- Muscle groups trained
- User goal
- Planned workout
- Available time
- Subjective fatigue
- User safety constraints

The engine should adjust the existing plan rather than generate a completely random workout every day.

Keep modifications explainable.

Examples:
- Low recovery: reduce intensity or volume.
- Moderate recovery: normal workout with controlled intensity.
- Good recovery and manageable load: normal training.
- High accumulated load: avoid unnecessary additional volume.

Do not diagnose overtraining or illness.

## AI Service

Implement a reusable AI service.

Build a structured context containing:
- User profile
- Fitness goals
- Health summary
- Readiness
- Baselines
- Training history
- Workout plan
- Recent recommendations

Use structured outputs and Pydantic validation.

AI is responsible for:
- Explaining calculated metrics
- Generating recommendations
- Providing conversational coaching
- Creating weekly summaries

AI must not calculate the readiness score from scratch or invent health data.

The AI must not diagnose medical conditions.

If data is insufficient, the AI must acknowledge the uncertainty.

## Database

Use PostgreSQL and SQLAlchemy.

Initial entities:
- Users
- UserProfiles
- WearableDevices
- HealthMetrics
- DailySummaries
- ReadinessScores
- TrainingPlans
- Workouts
- WorkoutExercises
- WorkoutSessions
- ExerciseSets
- FitnessGoals
- CoachRecommendations
- CoachConversations
- CoachMessages
- WeeklyReports

HealthMetrics must support timestamped data and multiple sources.

Store standardized values in regular database columns and source-specific metadata in JSONB.

Use UUID primary keys.

Use UTC timestamps.

Create migrations using Alembic.

## Engineering Rules

1. Build incrementally.
2. Do not implement the entire application in one step.
3. Before each milestone, inspect the existing project.
4. Never overwrite existing functionality without understanding it.
5. Use clean architecture.
6. Keep business logic separate from route handlers.
7. Use typed schemas.
8. Validate all incoming data.
9. Include loading, error and empty states.
10. Write tests for the readiness engine and training logic.
11. Use environment variables for secrets.
12. Never expose API keys in frontend code.
13. Document setup and commands.
14. Do not use hardcoded dashboard data once backend integration is complete.
15. Keep the product demonstrable at every milestone.
